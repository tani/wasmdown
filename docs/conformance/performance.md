## Compile-cost microbench and the policy experiment

`tools/compile-cost.lisp` compiles N generated functions (loop + locals +
branch + memory ops) and reports wall time and bytes consed, isolating the
cost of SBCL compiling one emitted lambda:

```
300 functions, 24099 bytes
  compile 0.20s  consed 212.0 MiB  (0.7 ms/func)
```

The recorded **negative** experiment: adding `(debug 0) (space 3)` to the
emitted lambda's `optimize` declaration moved this to 0.19 s / 209.6 MiB
(-1.2 % consing). The policy lever was measured and reverted; a reduction
must come from the emitted form itself (temp-slot count / tagbody size),
not from SBCL policy settings. The SQLite fixture's ~98 ms/function is the
same phenomenon at real sizes (2039 functions, 8 GiB), so this microbench
is the cheap proxy for that work.

## Compile-cost scaling with function size

`tools/compile-cost.lisp --functions 30 --repeat 2 --ops N` varies the
number of repeated statement blocks per generated function (each block:
an add/mul into a local accumulator, a conditional store and a store8):

| ops/body | bytes | time/function | consed/function |
|---:|---:|---:|---:|
| 1 | 7,922 (for 100 funcs) | 0.7 ms | 0.72 MiB |
| 4 | — | 2.3 ms | 2.21 MiB |
| 16 | — | 13.2 ms | 10.3 MiB |
| 64 | — | 175 ms | 80.4 MiB |

The cost per statement RISES with body size (0.72 MiB at 1 op →
1.25 MiB/op at 64 ops, and ~16× the time for 4× the ops between 16 and 64),
so the SBCL compile cost is superlinear in the emitted form. This is the
quantified form of the SQLite observation (~98 ms/function, 8 GiB for 2,039
functions): the lever is the emitted form's size (temp bindings and tagbody
length), not SBCL policy (the `(debug 0)(space 3)` experiment is recorded
above as a −1.2 % negative result; `(speed 1)` was also measured at the
16-op scale and is strictly worse — same time, 391 MiB vs 309 MiB consed —
so lower optimization is not a compile-cost lever either; and emitting the
temp slots as ONE simple-vector accessed through SYMBOL-MACROLET instead of N
lexical bindings is strictly WORSE at the SAME ops in a controlled A/B (20
functions, both modes, identical bodies): ops=16 lexical 13.2 ms / 10.1 MiB per
function vs array 41.5 ms / 24.9 MiB; ops=64 lexical 169.0 ms / 78.7 MiB vs
array 339.7 ms / 135.1 MiB). This rejects ONE replacement (array slots), not
the whole representation space: it changes both storage and every access, so it
cannot isolate binding count from access cost. The leading, UNPROVEN hypothesis
remains that the cost is SBCL compiling the large TAGBODY/GO graph; any
reduction must be measured against this table.

## Duplicate static validation on the compiled path (measured, not removed)

`instantiate` validates the module and then `compile-module-functions`
validates it again (a standalone guard at the public entry). Measured on the
SQLite Preview1 fixture: one `validate-module` costs **0.07 s and 33.5 MiB**
(median of 5, GC-preceded). Against the compiled lane's ~200 s / ~8 GiB for
2,039 functions that is 0.035 % of time and 0.4 % of consing, so the duplicate
is left in place: the standalone guard is part of the public contract and the
saving is immaterial.

## The embedded instance constant is not a compile-cost driver (measured)

Every emitted lambda binds `(inst ',instance)` — a quoted, circular module
instance — even when the body never touches memory/table/global/func
accessors. Measured directly by compiling 300 memory-free functions with and
without that binding/constant (temporary build, reverted): **0.09 s / 100.1 MiB**
with the binding vs **0.08 s / 99.8 MiB** without. The difference is noise, so
omitting the constant for instance-free functions is not worth the special
case; the cost remains in compiling the control graph of large bodies.
